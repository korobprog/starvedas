# План: карточки обрядов внутри раздела «Один обряд»

## Цель

В разделе **«Один обряд»** нужно сделать не одно общее текстовое поле, а удобный редактируемый список обрядов в виде карточек.

Администратор должен иметь возможность:

- нажать **«+ Добавить обряд»**;
- написать название обряда;
- добавить/изменить текст или описание обряда;
- указать/изменить цену обряда;
- создать сколько угодно таких карточек;
- редактировать карточки в любой момент;
- скрывать или удалять отдельные обряды;
- менять порядок отображения обрядов.

Клиент на сайте должен видеть эти обряды как варианты с галочками и выбирать один или несколько. После выбора сайт считает сумму по выбранным карточкам и отправляет человека на оплату.

---

## Согласованное решение

Выбран вариант: **отдельные карточки обрядов внутри продукта «Один обряд»**.

То есть:

- `Один обряд` остается основным разделом/продуктом;
- внутри него администратор создает любое количество обрядов-карточек;
- каждая карточка имеет свои поля: название, текст/описание, цена, активность, порядок;
- клиент выбирает конкретные карточки галочками;
- итоговая сумма считается по выбранным карточкам.

Это лучше, чем одно большое поле, потому что у каждого обряда могут быть свои цена и текст.

---

## Текущее состояние проекта

Сейчас:

- продукты/услуги хранятся в модели `Service`;
- раздел **«Один обряд»** уже существует как продукт со slug `single-rite`;
- клиентская форма сейчас выбирает один продукт через radio-кнопки;
- заказ (`Order`) сейчас связан только с одним `serviceId`;
- сумма считается от цены выбранного продукта и количества участников/имен;
- админка продуктов уже умеет создавать и редактировать продукты.

Чего сейчас не хватает:

- вложенных обрядов внутри продукта;
- выбора нескольких обрядов клиентом;
- индивидуальной цены и текста у каждого обряда;
- сохранения выбранных обрядов в заказе.

## Поля карточки обряда

Минимально нужны поля:

1. **Название**  
   Показывается клиенту в списке выбора.

2. **Текст / описание**  
   Дополнительная информация для клиента. Например: что входит, для чего обряд, особенности участия.

3. **Цена RUB**  
   Основная цена для оплаты в рублях.

4. **Цена USD / INR**  
   Если используется мультиязычность/валюты. Можно сделать необязательными, как у продуктов сейчас.

5. **Активен**  
   Если выключить — обряд не показывается клиенту, но может оставаться в старых заказах.

6. **Порядок**  
   Чтобы управлять отображением карточек.

Дополнительно можно добавить позже:

- короткое название для чека;
- фото/иконку;
- бейдж «популярное»;
- ограничение по датам;
- отдельный НДС/параметры чека.

## Клиентский интерфейс

На первом шаге формы клиент выбирает раздел, как сейчас.

Если выбран **«Один обряд»**, под ним появляется список карточек с чекбоксами:

```text
☐ Ганапати пуджа
  Описание обряда...
  1200 ₽

☐ Лакшми пуджа
  Описание обряда...
  1500 ₽

☐ Шани пуджа
  Описание обряда...
  2000 ₽
```

Правила:

- клиент должен выбрать минимум один обряд;
- можно выбрать несколько обрядов;
- если выбран другой продукт, эти карточки не показываются;
- выбранные обряды отображаются на шаге проверки заказа;
- сумма пересчитывается сразу при выборе/снятии галочек.

---

## Расчет суммы

Так как у каждого обряда теперь своя цена, сумма должна считаться от выбранных карточек.

Рекомендуемая формула:

```text
итог = сумма цен выбранных обрядов × количество участников
```

Пример:

```text
Ганапати пуджа — 1200 ₽
Лакшми пуджа — 1500 ₽
Участников — 2

(1200 + 1500) × 2 = 5400 ₽
```

Если позже понадобится цена «за заказ», а не «за участника», это можно добавить отдельным полем в карточке обряда. Но для первого этапа проще считать как цену за участника, потому что текущая логика сайта уже привязана к участникам.

---

## Что показывать на проверке заказа

На шаге проверки заказа нужно показывать выбранные карточки:

```text
Раздел: Один обряд

Выбранные обряды:
- Ганапати пуджа — 1200 ₽
- Лакшми пуджа — 1500 ₽

Участников: 2
Итого: 5400 ₽
```

## Что нужно хранить в базе

Нужно добавить сущность для карточек обряда, например:

```text
ServiceOption / RiteOption / CeremonyOption
```

Рекомендуемые поля:

- `id`;
- `serviceId` — связь с продуктом `Один обряд`;
- `title` — название обряда;
- `description` — текст/описание;
- `priceRub` — цена в рублях;
- `priceUsd` — цена в долларах, необязательно;
- `priceInr` — цена в рупиях, необязательно;
- `active` — показывать клиенту или нет;
- `sortOrder` — порядок;
- `createdAt`;
- `updatedAt`.

Также нужно сохранить выбранные обряды в заказе.

Лучше добавить таблицу выбранных позиций заказа, например:

```text
OrderServiceOption / OrderRiteOption
```

Рекомендуемые поля:

- `id`;
- `orderId`;
- `optionId` — ссылка на карточку обряда, если она еще существует;
- `titleSnapshot` — название обряда на момент заказа;
- `descriptionSnapshot` — текст/описание на момент заказа, если нужно;
- `priceRubSnapshot` — цена на момент заказа;
- `sortOrder`.

Snapshot важен: если администратор потом изменит цену или текст карточки, старый заказ должен остаться с теми условиями, которые были на момент оплаты.

## Как должна работать админка технически

### Добавление

1. Администратор нажимает **«+ Добавить обряд»**.
2. Появляется новая карточка.
3. Администратор заполняет название, описание и цену.
4. Нажимает **«Сохранить»**.
5. Карточка появляется клиентам, если она активна.

### Редактирование

Администратор может открыть карточку и изменить:

- название;
- текст/описание;
- цену;
- активность;
- порядок.

### Удаление/скрытие

Рекомендуемый безопасный вариант:

- для карточек, которые уже попадали в заказы, лучше делать **скрытие**, а не физическое удаление;
- для новых карточек без заказов можно разрешить удаление.

Так не сломаются старые заказы и отчеты.

## Что нужно изменить в публичной форме

1. Передавать на форму не только список продуктов, но и вложенные карточки обрядов.
2. Если выбран продукт `single-rite`, показывать карточки с чекбоксами.
3. Хранить выбранные `optionId` в состоянии формы.
4. Не давать перейти дальше, если выбран `single-rite`, но не выбран ни один обряд.
5. Считать предварительную сумму как сумму выбранных карточек × количество участников.
6. Показывать выбранные карточки на шаге проверки заказа.
7. Отправлять выбранные `optionId` на сервер при создании заказа.

---

## Что нужно изменить на сервере

Сервер должен считать сумму сам, не доверяя браузеру.

При создании заказа сервер должен:

1. получить выбранный продукт;
2. получить список выбранных карточек обряда;
3. проверить, что карточки существуют;
4. проверить, что карточки активны;
5. проверить, что карточки относятся именно к выбранному продукту;
6. если выбран `single-rite`, требовать минимум одну карточку;
7. посчитать сумму по актуальным ценам из базы;
8. сохранить заказ;
9. сохранить snapshot выбранных карточек;
10. передать корректную сумму в оплату.

---

## Что нужно изменить в оплате

В платежную систему нужно отправлять итоговую сумму по выбранным карточкам.

Описание платежа можно сделать таким:

```text
Один обряд: Ганапати пуджа, Лакшми пуджа
```

Если названий много, для платежки можно укоротить описание, но внутри заказа хранить полный список.

---

## Что нужно изменить в уведомлениях и админских списках

Выбранные обряды нужно показывать:

- в Telegram-уведомлении о новом заказе;
- в админке заказов/клиентов;
- в кабинете куратора;
- в списке участников;
- в экспортах, если они используются.

Минимальный формат:

```text
Выбранные обряды:
- Ганапати пуджа — 1200 ₽
- Лакшми пуджа — 1500 ₽
```

- Показать выбранные обряды в админке.

- Добавить выбранные обряды в Telegram-уведомление.
- При необходимости добавить в экспорт.

### Этап 6. Проверка

Проверить сценарии:

1. Администратор добавляет новую карточку обряда.
2. Администратор редактирует название карточки.
3. Администратор редактирует текст/описание карточки.
4. Администратор редактирует цену карточки.
5. Администратор скрывает карточку — клиент ее больше не видит.
6. Клиент выбирает один обряд.
7. Клиент выбирает несколько обрядов.
8. Клиент не выбрал ни одного обряда — сайт не дает продолжить.
9. Сумма на форме совпадает с суммой на сервере.
10. Сумма в платежной ссылке совпадает с заказом.
11. Старый заказ не меняется после изменения цены/текста карточки.

## Вопросы для согласования перед кодом

1. **Цена карточки считается за одного участника?**  
   Рекомендуемый вариант: да. Тогда итог = сумма выбранных обрядов × количество участников.

2. **Нужно ли поле цены только RUB или сразу RUB/USD/INR?**  
   Так как в продуктах уже есть RUB/USD/INR, логично сделать так же для карточек.

3. **Текст карточки нужен только на русском или также EN/HI?**  
   Если мультиязычность важна, нужно добавить название и описание RU/EN/HI.

4. **Удаление карточек разрешаем или только скрытие?**  
   Безопаснее: скрытие всегда, физическое удаление только если карточка не использовалась в заказах.

5. **Нужно ли менять порядок карточек drag-and-drop или достаточно поля “Сортировка”?**  
   Для первого этапа проще поле “Сортировка”; drag-and-drop можно добавить позже.

## Дополнение: оплата через Prodamus и разделение клиентов по доменам

### Что уже есть

В текущей реализации клиент уже проходит стандартный путь:

1. выбирает услугу/обряды;
2. заполняет ФИО;
3. заполняет email;
4. заполняет телефон;
5. переходит к оплате через Prodamus;
6. после создания заказа заказ появляется в системе;
7. после оплаты статус обновляется через уже существующий платежный сценарий.

Эту часть не нужно переделывать с нуля. Новая логика с карточками обрядов должна встроиться в существующий процесс создания заказа и оплаты.

---

### Новое требование: учитывать домен, с которого пришел клиент

Сайт может открываться через разные домены, например:

- `starvedas.ru`;
- `chintamanidhama.ru`.

Если клиент пришел через `chintamanidhama.ru`, заказ и клиент должны быть помечены как относящиеся к `chintamanidhama.ru`.

Если клиент пришел через `starvedas.ru`, заказ и клиент должны быть помечены как относящиеся к `starvedas.ru`.

Это важно для отчетов в кабинете администратора.

---

### Раздельные клиенты по доменам

Один и тот же человек может быть клиентом на двух доменах, и это должны быть **отдельные клиентские записи**.

Пример:

```text
Иван Иванов
Телефон: +7...
Email: ivan@example.com

Заказ через starvedas.ru       → клиент StarVedas
Заказ через chintamanidhama.ru → клиент Chintamani Dhama
```

Даже если телефон или email совпадают, система не должна автоматически склеивать этих клиентов в одного общего клиента.

Правило:

```text
клиент уникален не только по контактам, но и по домену/бренду
```

---

### Что сохранять в заказе

В заказе нужно сохранять источник, например:

```text
sourceDomain: starvedas.ru
```

или

```text
sourceDomain: chintamanidhama.ru
```

Также можно хранить человекочитаемый бренд:

```text
sourceBrand: StarVedas
```

или

```text
sourceBrand: Chintamani Dhama
```

Минимально достаточно хранить домен, потому что по домену можно определить бренд.

---

### Что показывать администратору

В кабинете администратора и отчетах нужно показывать, откуда пришел заказ.

Например:

```text
Заказ №123
Клиент: Иван Иванов
Сумма: 5400 ₽
Статус: Оплачен
Источник: chintamanidhama.ru
```

Или бейджем:

```text
[chintamanidhama.ru]
```

Для заказов со StarVedas:

```text
[starvedas.ru]
```

---

### Фильтры в кабинете

Желательно добавить фильтр по источнику:

```text
Все источники
starvedas.ru
chintamanidhama.ru
```

Так администратор сможет смотреть:

- все заказы вместе;
- только заказы StarVedas;
- только заказы Chintamani Dhama.

---

### Что показывать в Telegram-уведомлении

В уведомлении о новом заказе желательно добавить строку:

```text
Источник: chintamanidhama.ru
```

или

```text
Источник: starvedas.ru
```

Так сразу будет понятно, с какого сайта пришел клиент.

---

### Как определять домен технически

При создании заказа сервер должен определить домен из запроса:

```text
Host / X-Forwarded-Host
```

Далее нормализовать его:

- убрать `www.`;
- привести к нижнему регистру;
- оставить только разрешенные домены.

Если домен неизвестный, можно использовать значение по умолчанию:

```text
starvedas.ru
```

---

### Важное правило безопасности

Нельзя доверять домену, который клиент отправляет из браузера в JSON.

Правильно:

- клиентская форма может ничего не отправлять про домен;
- сервер сам берет домен из request headers;
- сервер сам записывает источник в заказ и клиента.

---

### Что нужно изменить в базе

Минимально:

1. В `ClientProfile` добавить поле:

```text
sourceDomain
```

2. В `Order` добавить поле:

```text
sourceDomain
```

3. При поиске/создании клиента учитывать `sourceDomain`.

То есть клиент должен искаться примерно по логике:

```text
контактные данные + sourceDomain
```

а не только по телефону/email/Telegram.

### Как это связано с карточками обрядов

Карточки обрядов и домен-источник — две разные задачи, но они встречаются в одном сценарии заказа.

Итоговый процесс должен быть такой:

1. Клиент заходит на сайт через `starvedas.ru` или `chintamanidhama.ru`.
2. Выбирает раздел **«Один обряд»**.
3. Выбирает одну или несколько карточек обрядов.
4. Заполняет ФИО, email и телефон.
5. Переходит к оплате Prodamus.
6. Сервер создает заказ с выбранными обрядами и `sourceDomain`.
7. После оплаты администратор видит заказ в кабинете.
8. В отчете видно, с какого домена пришел заказ.
9. Клиенты с разных доменов считаются отдельными клиентами.

### Дополнительные проверки

Нужно проверить сценарии:

1. Заказ через `starvedas.ru` получает источник `starvedas.ru`.
2. Заказ через `chintamanidhama.ru` получает источник `chintamanidhama.ru`.
3. Один и тот же email на разных доменах создает двух разных клиентов.
4. Один и тот же телефон на разных доменах создает двух разных клиентов.
5. В админке у заказа отображается правильный источник.
6. В Telegram-уведомлении отображается правильный источник.
7. Фильтр по источнику показывает правильные заказы.
8. Оплата Prodamus продолжает работать без изменения пользовательского сценария.
